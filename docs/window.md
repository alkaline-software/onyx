# The window

About `crates/onyx-app/src/shell.rs`, `tabs.rs`, `ui_state.rs`, `main.rs`, `settings.rs`, and `crates/onyx-core/src/vault.rs`: the vault, a note's life, the tabs, the sidebar, the strip, the landing page, the sheets and menus, and what the window remembers.

## Rules

- **A note is written whole** (`vault::write`: a temp file beside it and a rename), never in place and never in part: a sync or another app reading the file sees the old note or the new one.
- **A note saves itself, as Obsidian's do.** Its first change since the last write marks it dirty and starts a timer (`Shell::note_changed`, `SAVE_AFTER`, two seconds); later keystrokes do not put the timer off, so typing without a pause is one write every two seconds, never one per keystroke, and no more than two seconds of words live only in the window. The timer finds its tab by its editor, which a rename keeps. A note is also written when another tab shows (`show_tab`), when the window is left for another app (`observe_window_activation`), when its tab closes (`close_tab`), before the vault closes or changes, when the window closes, at quit and before an update installs (`save_all`). A write whose text is what the disk has already is skipped (`save_tab`), so typing and taking it back costs nothing. There is no ⌘S and no dot on a tab: nothing waits to be saved by hand. (Obsidian 1.15's `TextFileView` does the same: a two-second timer that is not reset, a write when the editor loses focus, and none when the text is the last written.)
- **A note with changes is never replaced by the disk's text.** A note with none takes it whole and quietly (`Editor::replace_text_quietly`). A note with changes joins it with what was typed (`disk_text`, `onyx_core::merge::merge`): each side's changes are found line by line against the text last written or read (`Tab::saved`), every one is kept, and where both changed the same lines differently the window's come first and the disk's follow. The result goes in as one edit, one step of undo with the caret kept, is written at the next save, and is said under the strip quietly, in the muted ink with a merge icon (`say_quietly`), since it is news and not a failure; a failure is said in the danger's ink (`say`). Onyx's own write coming back from the watcher is nothing, since `saved` holds it.
- **A note or a folder deleted goes to the system's trash** (`vault::trash`), never `remove_file`.
- **A rename refuses a taken name** and a name with a slash, and keeps a note's extension (`vault::rename`); the open note follows its new path, and so does a note inside a renamed folder, and so does everything else that knows a note by its path (`Shell::rename_entry`: Wide, the last note shown, the closed tabs). Anything new kept by path goes there too. What must survive a rename is keyed by the note, not the path: a page's fade in is keyed by its editor (`render_page`), or a rename replays it.
- **The tree is read off the disk, never kept in step by hand.** After a change of Onyx's own, `reread_tree`; after another app's, the watcher.
- **The vault's folders of its own are not shown** (`.obsidian`, `.onyx`, `.trash`, `.git`, and anything that starts with a dot), and only notes (`.md`, `.markdown`) are listed.
- **Each tab has its own editor** (`Tab::editor`): the text, the caret, the scroll, the undo history and the dirty state stay with the tab while another shows, and a change to the faces, the size or the mode reaches every editor (`push_look`, `set_mode`). The editor's events name the tab they are for by its path, and a rename gives the editor a new listener under the new path. Tried and dropped: one editor handed each tab's text in turn, which lost the caret, the scroll and the history at every switch.
- **A size the next frame depends on is figured as the frame is built, never measured off the last one.** While a frame is drawn, gpui's `cx.notify` asks for no other frame (`invalidate_view` marks the window dirty only outside a draw), so what a canvas reads in prepaint waits for whatever draws next. With the pointer at rest after a window was resized by a key, nothing did: the tabs stayed at the old row's widths and place. The row's width and the page's come from the window's and the sidebar's (`Shell::render`).
- **Nothing under what stands over the window scrolls.** A sheet, the search, the viewer, a menu or a flown card says so as it is drawn (`Scrollers::over`), names its own scrollers with `name_over` (a flown card drawing the notes card lifts it, `Scrollers::lift`), and the scroll router gives the wheel to those alone, or to nothing; while a panel of the system's stands on the window as a sheet (the printing panel), nothing scrolls or follows the pointer (`sys::sheet_over`). The router hands the wheel to scrollers by their bounds, not gpui's hit test, so a new layer over the window that does not say so leaks the wheel to the note under it.
- **One note, one writer.** While the menu bar note and a tab hold the same file, the tab writes it and the menu bar note only follows (`menubar.rs`); with no such tab the menu bar note writes it itself. Both editors hold one text as it is typed (`Editor::follow_text`, which says nothing, so neither marks the other's typing as its own). Two writers each saved the same text on their own clock and each read the other's write as a change on the disk.
- **Nothing that opens, focuses or closes a window runs inside the update of a view that window draws.** gpui draws a new window as it opens it, and a view drawn while it is being updated panics (`cannot update … while it is already being updated`). The menu bar note opens and focuses its window a moment on (`MenuNote::open`, `with_window`), and what the main window tells it is deferred (`menubar::follow`, `written`), since the note may be the one asking the main window, busy until it returns; the main window reads which note it holds from a shared cell (`MenuBarNote`), never from the note.
- **Everything the window remembers is written through `UiState`** (`save_ui`), never read from `Config`: the vault and the note are state, not settings.

## The vault

A vault is a folder. `vault::tree` reads it whole, folders first and then notes, each in the file manager's order (case folded, a number by its value, so Note 2 stands before Note 10), and the window keeps the result as `Vault::tree`. The folder is watched (`vault::watch`, the `notify` crate) from the moment it opens; the watcher's thread sends the paths that changed down a channel the window looks at every 300 ms (`watch_changes`), and a burst of them is one reading of the tree off the main thread (`disk_changed`). A note gone from the disk is closed.

The vaults live in one folder, the container (`AppConfig::container`), and every folder at its top but dotted ones is a vault (`vault::vaults_in`); there is no vault anywhere else. The container is a setting, not a level: chosen once and seldom changed, as Obsidian's place for vaults is chosen while making one and Craft's spaces are switched from one tile, it never stands in the sidebar, which is only ever the vaults or one vault's notes. It is chosen in the system's own folder panel (Choose Container…, `choose_container`, through `cx.prompt_for_paths`, from the first page, Settings, General, Container, Change…, which asks it of the main window, and File, ⌘⇧O): a folder there already, each folder in it a vault as it is, or a new one made with the panel's New Folder; the panel goes through every folder on the machine and iCloud Drive with it, so Onyx has no sheet of its own for it. A vault wears its own mark wherever the sidebar or the page names it (`library::vault_badge`: its first letter on a rounded tile of the accent, as a space has its tile in Craft, or the icon and color it was given, A folder's look below): the vault's button, and where a vault stands as a block, the vault's row over its tree, the list of vaults and the page's tiles, the badge at the front of a deck of two more of its shape (`vault_stack`), the block in a wash of the vault's ink with an edge of it, well taller than a folder's row (`VAULT_BLOCK_H`); a folder has a folder's icon and a note a note's, so the three never read alike. With a vault, the card is its tree and the button under it the vault's (Close Vault, `close_vault`, back to the vaults); with none, the card lists the container's vaults and there is no button. One vault is open at a time. Tried and dropped: the container as a level of its own, a card of its vaults and a button with Close Container, then as folders opening to their vaults on one card, both of which drew a container, a vault and a folder as rows of one kind; and a New Container sheet offering iCloud Drive or a folder in Documents, which named a folder that was not there yet. It is taken by `use_container`. Nothing is made in a vault until it is needed: its `.assets` comes with its first asset (`vault::claim`), its `.onyx/folders.json` with its first folder's look, so a folder of ten folders taken as the container is left as it was. Taking another container closes the vault shown, so the page and the sidebar list the new one's vaults. Before there was a container a vault could be anywhere, so at launch, with none chosen, the folder the remembered vault is in becomes it (`Shell::new`), and the vault shows as before; a vault remembered from another container does not. `library::vault_list` is the list everywhere (the page's and the card's, the vault's button's, the menu bar note's): the vault shown first, then the container's vaults shown before, the last first (`UiState::remember_vault`, twelve kept), then the rest by name.

Showing a vault (`show_vault`): the note showing is written, the tree read with every folder shut, the watcher started, and the vault put first among the recent ones. The tree keeps the folders open (`Vault::unfolded`), not the shut ones, so a folder never seen is shut; only at launch are the folders left open in the vault shown last opened again (`ui.json`'s `unfolded`). Tried and dropped: Open Folder as Vault…, which took any folder on the computer as a vault, so the vaults were wherever they had been opened; one folder holding them all is simpler to keep and to sync.

A new vault (`start_new_vault`, from the page, the card's Vaults row, the vault's button's list and File, New Vault…) is a sheet with the name in a field, Notes to begin with; it goes in the container. With no container New Vault… asks for one first. ↩ or Create makes the folder (`vault::new_vault`, which keeps a folder of that name that is there already, so a vault synced from another machine is not refused, and refuses a file of that name) and shows it. What the app library takes is in `docs/platform.md`, iCloud Drive.

The watcher's changes are sifted before anything is read (`Shell::change_matters`): only a note, a folder, something gone that could have been one, and nothing under a dotted folder. A picture copied in, iCloud's bookkeeping and Obsidian's `.obsidian/workspace.json` cost no reading and no frame.

A wikilink names a note by its stem (`vault::resolve_link`): the link's own folder first, then the shortest path anywhere in the vault; a path with a slash is from the vault's root; a heading or an alias after `#` or `|` is dropped. A wikilink to no note makes the note at the vault's root, as Obsidian does (`open_wikilink`); one that names a file that is not a note (`[[plan.pdf]]`) opens that file with the system's app. A link that is a path is found as an attachment is (`vault::find_file`, below): a note of the vault opens here, any other file with the system's app; an address opens in the browser (`open_link`).

### The tree's choice and moves

The notes' tree is a list to work in, after Emaki's files panel (`shell/tree.rs`, `emaki/docs/panels.md`, Choosing rows and Moving).

- A click on a row chooses it alone and opens it (a note) or folds it (a folder); ⌘ and a click adds the row to those chosen or takes it out; ⇧ and a click chooses from the row last clicked to this one (`tree_click`, `Choice::anchor`). A press in the room around the rows lets the chosen go and starts a rectangle that chooses every row it reaches (`band_start`, `band_to`); every row is one height and the list starts at the scroller's top, so the rows are found by number. With none chosen the note showing is lit. A row is `TREE_ROW_H` tall and its lit plate stands `ROW_BREATH` in from its top and foot, so a row lit or under the pointer breathes apart from the next; rows chosen one under another drop that room where they meet and are one block, round at its two ends (`lit_joins`). The list starts `LIST_TOP` under the card's band. The press and the pointer are the row's whole height, its plate lit through a group (`tree-row`), so the room between plates is no dead line. The assets' rows are made the same way. A right click on one of several is their menu (Cut, Copy Paths, Move n Items to Trash); on any other row it chooses that row alone.
- The keys, while the keyboard is in the tree (`TREE_CONTEXT`, the click puts it there): ↑ and ↓ go from row to row, ⇧ with them grows the choice; → opens a folder or goes into it, ← closes it or goes up; ↩ opens the note; ⌘⌫ puts what is chosen in the trash, a folder chosen with what it holds once; ⌘A chooses every row showing; ⌘X cuts (drawn faint) and ⌘V moves what was cut into the folder the keys stand on; Esc lets the choice go.
- A row is dragged to move it, with the others chosen when it is one of them (`TreeDrag`, `drag_of`); let go over a folder it goes in, over a note into that note's folder, over the room around the rows to the vault's top, and the row under it is washed in the accent while it is held there. A row already there stays, a folder never goes into itself, and a name taken there refuses the whole move before anything moves (`vault::planned_moves`).
- A move keeps every link going where it went (`move_items`, `vault::move_into`, `vault::relink_moves`): a note moved keeps its own links, paths written again from its new folder, and the others' links to what moved follow, wikilinks with a path included. An open note's changes come from what its editor holds, as one step of undo written with the note; every other note's file is written whole. What knows a moved entry by its path follows it (`follow_moves`, which a rename goes through too): its tab, the note shown, the tabs closed, the folders folded.

### Assets

One folder at the vault's top holds every note's pictures and files, not one per folder as Obsidian can keep them: `.assets` (`vault::ASSETS`, `vault::assets`). It is dotted so that it is never a folder of the person's own of the same name, and so the tree and the watcher's sifting pass it by as they do `.obsidian`; the sidebar's Assets card shows it instead (below). A note made elsewhere that keeps its pictures in a folder of their own still finds them (`find_file`). Obsidian leaves dotted folders out of its index, so a picture in `.assets` does not show in Obsidian.

A file comes in by a paste (files copied in the Finder, or a picture copied alone, which is kept as `Pasted image <time>.png`) or a drop on the page, where the caret goes first (`Editor::attach`). It is copied into the folder off the window's thread under its own name or the first free one after it (`scan 1.pdf`), each name claimed by making it empty only where nothing is, so two coming in at once never share one, and filled through a temp file and a rename (`vault::copy_asset`, `add_asset`). A file in the vault already stays where it is. The note then refers to it in standard markdown, so any other app reads it (`vault::reference`): `![name](../.assets/a.png)` for a picture, `[name](../.assets/plan.pdf)` for any other file, the path from the note's folder with spaces and brackets as `%20` and their like, each a block with a blank line between it and the words on either side, on its own line or the next, so a picture is drawn here and elsewhere.

A link or an embed finds its file (`vault::find_file`) as written from the note's folder, then from the vault's top, then by its name in `.assets`, then anywhere in the vault outside a dotted folder by the shortest path, so Obsidian's `![[a.png]]`, a markdown path and `<img src>` all find the same file, and a note moved to another folder still finds its pictures.

The vault is the card (`render_side_stack`). Its top is a pair of tabs after a design of Emaki's: Notes and Assets, each half the width, an icon and a name, on a tinted band with a hairline under it, its top rounded as the card's: gpui's rounded corner does not cut what is drawn inside it, so a band drawn square stood out of the card's corners. The one open stands on a plate, raised in the frame's own ink (`theme` is the frame's, `frame_theme`); a press on the other slides the plate across and the card's content fades in. Notes is open at first; the card open is remembered in `ui.json` (`side_view`). Under Notes the vault stands at the top of its tree as the menu bar note's does (`render_vault_row`): a folder's row that does not scroll with the tree, the vault's name, and at its right Collapse All Folders (`collapse_all`), New Note and New Folder, always there, the last two making at the vault's top (⌘N makes beside the note showing). A right click on it gives the vault's menu, Rename (`rename_vault`) and Reveal in Finder, and a row let go on it goes to the vault's top. A folder's row has its own New Note and New Folder while the pointer is on it, in the columns the vault's stand in, so each icon stands over its own kind; no room is kept for them else, so a name is cut only while they show. The row the pointer is on is the view's (`hover_row`, set by `on_hover`): a hover style is applied as the row is painted, after its layout, so a width given on hover never showed. Renaming the vault writes the open notes, renames its folder (`vault::rename`), watches the folder at its new place, and moves every path that knew the old one, the open tabs, the open folders, the menu bar note's and the recent vaults, as a folder renamed inside the vault moves them (`follow_moves`). Under the card stands the vault's button (`render_vaults_button`), a slim card with the vault's mark and name and the arrows of a list: the vault shown, and the way to another. A press opens the vaults' list in a menu as wide as the button, rising from its top (`show_vaults_at`, `Menus::show_above`), and a press while it shows puts it away; the button stays lit while it shows. The list is `vault_list`, the one shown ticked, then New Vault… and Close Vault. Tried and dropped: the vault on the card's head, its name on a chip with the three buttons beside it over the tabs, which made the top of the sidebar three rows of controls; the other vaults as a slim card each under the card, three at most and a tab hung from the last for the rest, which took room from the tree for vaults seldom opened; two icons alone on a segmented control, whose raised plate took the light theme's ink on the dark frame; and a stack of cards after Emaki's computers, the one shut a row in a slim card at the sidebar's foot, which put the second of only two things far from the first.

The Assets card (`shell/library.rs`, `render_assets`) lists every file of `.assets` at any depth, but dotted ones (`vault::asset_files`), by its kind (`preview::kind`), a row each with the file's whole name, each group under its name and count: pictures first, each on a taller row (`PICTURE_ROW_H`) with its small square in the icon's place, cut from the picture's middle, drawn small off the window's thread once (`draw_thumbs`) and fading in when it arrives, large enough to tell one picture from another; then documents, media and the rest with their file icons. A grid of squares was tried first and lost the names. The list is read again off the main thread whenever the watcher says something in `.assets` changed (`assets_changed`, `reread_assets`). A press opens the file in a tab (`open_asset`); a drag puts its link in a note where it falls, as a drop of a file does (`AssetDrag`); a right click opens its menu: Rename, Open, Open with Default App, Reveal in Finder, Copy Link (the reference a note would write, from the note showing), Copy Path, Move to Trash.

An asset opens in a tab beside the notes, a tab like any other (`Tab::asset`): it takes its place in the row, its group is the `.assets` folder's pill (named Assets on its hover), ⌘W, ⌘⇧T and the tabs remembered across launches treat it as a note's, and `open_note` sends any file that is not a note to `open_asset`. Its name is the file's whole (`tab_title`). It is read only: its editor reads only (`Mode::Reading`), it is never written (`save_tab`, `note_changed` pass it by), and Print and Export are a note's alone; where a note's path bar has Export, an asset's has Open with Default App, except a picture's or a PDF's, whose frame has its own bar. The file is read off the main thread (`preview::read`): what can be read as markdown (text and code as a block of code, markdown itself, a table of CSV, a notebook, HTML, a Word document, a deck, a workbook's sheets) is drawn by the tab's own editor on a note's page, its title the file's name, its links followed as a note's (`render_note`); a picture and a PDF in the frame a note shows a PDF in (`Body::Frame`, `Embed::for_tab` in `embed.rs`), filling the page less its margin, its bar coming while the pointer is on it and fading as in a note (`Embed::settle_bar`, which the frame asks itself in a tab, with no note to ask it), over room of its own: the first page or the picture stands the bar's height and the margin down (`Embed::inset_top`), so the bar never covers the file until it scrolls. The bar holds the file's icon and its name, which a click renames as the note's bar does (every link following, and the tab, the path and the bar with it, `Asset::moved_to`); for a PDF the sidebar's button and the page it is on; the zoom as − 100% + (a press on the share goes back); for a picture View, which opens the viewer from where the picture stands, as a double click on it does; and the menu, the assets card's less Open (`show_asset_menu`). Nothing of a line is there: no place across the page, no width, no pencil. With no zoom chosen a file shows at 100% (a picture's pixel to a point, a PDF's page at its size in points, `preview::pdf_sizes`) or less, as much as the frame's width holds, never more, on the frame's ground with a margin round it; ⌘+ and ⌘- step through the frame's zooms and ⌘0 goes back, from the View menu too, as ⌘ and the wheel or a pinch zoom about the pointer. A picture is sized from its header (gpui gives a picture its own ratio, which wins over a box of the room's height) and stands as a PDF's one page does, so the frame's zoom and scroll serve both. A PDF has all the frame has in a note: every page drawn as it comes into view, its words selected and copied (read for the tab when it opens, `Embed::read_text`), the sidebar with its small pages and its outline or contents. The frame measures itself after each layout (`Embed::sizer`), as a note's frame has its row's size. a video or a sound in the system's own player (`media.rs`, after Emaki's `html_web.rs`: a web view set in the window over the page, shown once the page has faded in, and only while its tab shows with no menu, sheet, search or flown card over it, `sync_players`, since it is drawn over the window's drawing; its file handed out a range at a time under a scheme of ours that serves that one file; the keyboard is handed back to the window when it hides or goes, `sys::keys_to_window`; Linux has none and says so); anything else says why, with Open with Default App on it.

Renaming an asset (Rename on its menu or its tab's, the rename sheet as for a note, Rename File) keeps its extension and follows every link to it (`rename_asset`, `vault::relink`): a markdown link's or picture's address, in angle brackets or not, a wikilink's or an embed's target with its alias and size kept, and an HTML `src` or `href`, each written as it was (a bare name stays bare, a path stays a path from the note's folder, what follows `#` or `?` kept), and a link's words that were the old name become the new. A link counts as the file's when it finds that file (`find_file`), so the changes are found before the file moves. A note open in a tab is changed through its editor, from what the editor holds, as one step of undo written with the note (`Editor::apply_edits`); every other note's file is written whole (`vault::rename_asset`). Code is left alone.

## A note's life

`open_note` reads the file, makes a tab for it with an editor of its own (`make_editor`: the look, the mode, the text, and the listener for its events), puts the tab at the end of its folder's pill (`sort_tabs`) and shows it (`show_tab`), with the keyboard in its editor. A note already open just shows. The editor says when its text changed (`EditorEvent::Changed`), and the window writes it as the rules say. A new note asks its name first (`new_note_in`, `start_making`): the name sheet comes up as New Note with the first free "Untitled" in its field, selected to type over, and nothing is on the disk until Create or ↩ (`finish_making`, `vault::create`), which makes it under that name exactly, refused and said when the name is taken, and opens it; Cancel and Esc leave nothing behind. It goes in the open note's folder, else the vault's top (never `.assets`, when an asset shows). A new folder likewise. Made first and named after, a note cancelled at its name was left as `Untitled.md`. Both come from the sidebar's buttons, File, ⌘N and ⌘⇧N, or a folder's menu.

## The tabs

`tabs.rs` draws them for any window that holds tabs, a `TabHost`: the main window (`Shell::tabs`, in the row's order, and `shown`) and the menu bar note (`MenuNote::tabs`). The row asks its window only to show, close and reorder a tab, its menus, the plus, and to take a press; everything here holds in both. As emaki has one tab per open session, Onyx has one per open note, and a folder's tabs stand together on one pill (`Tabs::group`, at every draw): the segmented control's track, with the folder's mark at its left end (its hover names the folder from the vault's root, or the vault) and the note showing on a raised plate. The pills are in the order their first tabs had, and a tab opened lands at the end of its folder's pill.

The plate is one element under a pill's tabs. It slides to another tab of the same pill, and between pills it fades out of one and into the other: a plate does not leave its track. It is placed by sum, never measured, since every width in the row is ours, and it reads the same clock the tabs' widths do (`Width::now`), so it keeps its tab while they move.

A tab is as wide as its name needs (`Tabs::sync`, at every draw): the title measured once in the tab's type at the showing tab's weight (`Tabs::fit`, by the theme's face, since the shell's render runs before any element's style is in force) plus the tab's edges, its close button and its outline, never under `TAB_LEAST`, a comfortable tab for a short name, nor over `TAB_MAX`. Once the row has no room for every tab at its own width, the widest give way first (`Tabs::share`): one cap is set so the row is filled, every tab wider than it is cut to it, and the narrow keep their width; the cap goes no lower than `TAB_MIN`, and past that the tabs keep their widths and the row scrolls sideways, with the tab shown brought into view: with its pill's mark where both fit in the row, else the tab alone (a pill wider than the row, brought in from its mark, left a tab opened at its end outside), and `REVEAL_ROOM` past it so the edge's fade is not over it; the row is centered while the tabs and the plus fit, and runs from the left once they do not, which is a padding of ours (`Tabs::lead`) and not the row's own centering, so it can move. The plus is never scrolled away: it stands beside the scrolling tabs, not among them, right after the last while they fit and at the row's end once they fill it. An edge of the tabs with more past it fades into the bar's ground over `FADE_W`, coming in as the scroll leaves that end (`side_fade`); cut by the row's edge, a pill ended in a hard straight line. A new tab grows in from nothing while the others give way, a closed one's room is taken up the same way, and a new pill's track is let out with its tab, each over `TAB_ANIM`. Whatever changes the row's room, a window resized or the sidebar moved, every width, the lead and the scroll that brings the tab shown into view head for their new values from where they stand (`Width::head`, `TAB_ANIM`), so the tabs glide; asked again at every frame of a drag, they follow it and catch up when it stops. The window asks for a frame while anything in the row moves (`Tabs::moving`). A width's animation element keeps its id through all of this: it is there to read the clock, and a new id at each step would lose a press on a moving tab. Tried and dropped: the flex row sizing tabs to their titles and shrinking them itself, which drew a new tab at full width for a frame.

A tab is dragged along its pill and a pill along the row by its handle, the folder's mark, with the name on a ghost under the pointer and the one being moved drawn faint (`DragTab`, `DragPill`, `Ghost`; the row's `on_drag_move` hears both). The tab or pill stands after every neighbor whose middle the pointer has passed (`drag_tab_to`, `drag_pill_to`): going by the middle keeps two of different widths from changing places back and forth under a pointer that is still. The one tab of a pill takes the pill with it. Each neighbor that changed places slides to its new place from where it is now (`Shift`), the plate going with the showing tab, and the pill being moved is painted over the ones it passes (`deferred`). The row's new order goes to the shell (`Shell::reorder_tabs`), which keeps `Shell::tabs` in it and remembers it; `Tabs::group` keeps a drag's order since pills stand in the order their first tabs have. A press on a tab or a handle is the start of its drag, not the window's (`press_taken`, below).

⌘ held alone for half a second shows each of the first nine tabs its number on a small plate half over its lower edge, with an outline on every tab, and they go when the key is let go or another joins it, so a quick ⌘C never sees them (`Tabs::modifiers_changed`, from the shell's `on_modifiers_changed`; a release the window did not hear, after ⌘Tab away, is caught at the next draw). A probe shows them with `ONYX_GO=hints`.

- **Shells.** The person's login shell in the vault's folder (their home when that is gone), started so its prompt marks itself (`onyx_core::shell_marks`, OSC 133), a tab each in its head: the first is made when it is first shown, + makes another (⌘T, ⌘N), a tab's button closes it, ⌘W closes the tab showing and with none left puts the terminal away (`TermEvent::Away`). A tab is pressed to show it, the screen fading in over the one before, dragged to move it, and grows in when new; ⌘⇧[ and ⌘⇧] go along them. A shell gets no `ONYX_*` variable, so a probe's vault never reaches a relaunch from it, and a UTF-8 character type where the app has no locale (one opened from the Finder has none): without it zsh counted é and 世 as several columns and drew the cursor off its letters.
- **The screen** (`onyx_core::pty`, `vendor/vt100`): Kaku's scheme for the window's appearance or the one chosen, the window's code face with Kaku's fallbacks at 13, a row 1.32 × 1.15 of the letters, 15 of room round it; a resize reflows the shell's lines; a pty writes from its own thread, so while the terminal shows a task looks every 33 ms and draws again when the screen changed (`watch`).
- **Keys** are Emaki's: a Mac's terminal keys (⌥ and ⌘ with arrows and Backspace, ⌘K clears, ⌘A the paragraph being typed), what is typed edited as a field's text by steering the shell's cursor, Shift with the keys that move a caret selecting, the keys that scroll back. Tab and ⇧Tab are the shell's (`TERMINAL_CONTEXT`); off a Mac every Ctrl and a letter is the shell's.
- **The pointer** is Kaku's: a drag selects (a double click the word, a triple the row, ⌥ the same columns of every row) and is followed anywhere in the window, scrolling at the screen's edges; the selection is copied when the button is let go, with "Copied" shown; a click that selects nothing puts the cursor there; ⌘ and a click opens a link or a file; the middle button pastes; the right one opens the window's menu (Copy, Paste, Select All, New Tab, Close Tab, Clear: `menu_do`). A program that asked to hear the mouse hears it, unless Shift is held. Files dropped on it are typed as their paths, and a picture pasted is kept in the cache and pasted as its path.
- **Settings, Terminal** (`TerminalConfig`): the scheme, the cursor's shape and whether it blinks, ligatures, and copying a selection when the button is let go; the face is the code face, set in Font.
- **Find** (⌘F on the screen, `find_open`): a card at the screen's top right as the note's find bar is drawn, looking through the screen and all it keeps of what has left it (`find_run`), without regard to case unless what is looked for has a capital. Every match is washed in the cursor's ink, the one that stands stronger; a new phrase stands on the newest match, the one nearest the prompt, brought into sight a third down the screen (`find_show`). ↩ and ⌘G go to the next, ⇧↩ and ⇧⌘G to the one before, round the ends; Esc, the close button or ⌘F in the field closes it and gives the keyboard back to the screen. A selection on the screen is what it opens looking for. While the screen changes the matches are looked for again, at most every 300 ms. Emaki's terminal has no find; this one is Onyx's own.

A picture is painted in one color, so the drawing is layers of one color each, in the icon's own colors whatever the accent or the appearance: the stone's glow under it, base, inner light, teal edge and rim light, the notebook's pages, cover, lines and bright line; the pen is one color, the lines' gray in the light appearance and the pages' warm white in the dark (the window's foreground was tried and was too hard beside the picture), so it shows on either ground, with its nib's slit in the paper's and an edge in the ground's color under it, so it stands off the stone and the lines it crosses. The stone's and the pen's layers are pictures in `icons/home/`, the stone's traced from the same superellipse as the icon's (`mP` in `scripts/icon/icon.html`). A layer's shading is its picture's alpha (a gradient's stop opacity, a path's fill opacity), which gpui keeps when it paints the picture in one color, so the stone's glow and light are soft though each layer has one color; the notebook's five are made as text at each draw with its tilt written in, rounded to half a degree, and handed over as data (`svg().data`), since gpui turns a picture only after it is rasterized and a line turned that way blurs; each tilt is rasterized once and kept by its text's hash. It answers the pointer on a spring (`widgets::Fig`, emaki's `HomeFig`, with a third value for how near the pointer is): the notebook tilts and lifts toward it, the pen comes to the page and writes the bright line as far as the pointer has come across, then goes back to lie by the stone with the line whole, and the window asks for a frame while the spring moves. Under it the greeting by the hour and the account's first name (`greeting`, `sys::user_first_name`), in the note's face so the page and the note agree, and then what can be done next on pills with their keys at the right: New Note, New Folder, Reopen Closed Tab while there is one. Each page fades and rises in (`page_in`) when it arrives.

## The menu bar note

MiniNotes, the menu bar app Onyx took the place of at v0.5.0, comes back as a part of Onyx (`menubar.rs`): one markdown file, any on the disk, in a small window hung from Onyx's item in the menu bar. Its look is MiniNotes'; everything under it is Onyx's.

- **The item** (`sys/status_item.rs`, taken from Mado's) is the app icon in one ink, a template image 18 by 16 points: the page upright with its three lines, the pen writing on the middle one, the plump pebble of onyx under them, level and the same on both sides, with its shine cut out of its far shoulder where the page does not cover it (`icons/menubar-note.svg`); a vein cut straight across the old slab read as a coffee bean's groove at this size; while the note is open the page is filled and its lines cut out of it (`menubar-note-open.svg`), as the system's input menu badge fills while engaged. Where two parts cross, the one behind is cut back by a gap (an SVG mask), since one ink would merge them. MiniNotes' badge, a rounded box with a pen, was the item until the app's own picture took its place. A left click opens or closes the note; a right click, or Control and a click, shows the system's menu: Open Onyx · Settings…, Check for Updates… · Quit Onyx, named again when the language changes (`menu_bar_lines`). Settings… and Check for Updates… open the main window first when it is shut, since the settings are its (Check for Updates… opens them on About and looks). A menu bar manager may push the item off the screen and the system keeps that place, so it is put back in sight two seconds after launch, before the note opens and when Onyx is opened again (`heal`, MiniNotes' `healStatusItemIfNeeded`). Onyx stays in the Dock: the item is a way in, not the app's home.
- **The window** is MiniNotes' size, 620 by 500, a card with the window's ground hung from the item by an arrow that points at it, kept 8 in from the screen's sides, the arrow moving along the card's top to stay under the item (`MenuNote::place`). With the item hidden it hangs from the top of the first screen's middle. It is gpui's pop-up panel, which does not make Onyx the app in front, so the main window stays where it was under the other apps; it floats at the floating level, not the pop-up menu's, or an input method's candidates show behind it (`sys::float_note_window`, MiniNotes' lesson). It is made borderless, and the toolkit's root under it is given a clear ground: gpui's panel is titled, and the system drew a titled window's rim and backing round the whole of it, the arrow's strip too, with a square shadow, and the root laid the theme's ground over the window. A new style mask rebuilds the window's frame and makes the window itself its first responder, so gpui's view is made the first responder again after it: without that a click reached the note and no key did, and nothing could be typed. As it is, the card and the arrow are its shape. It comes in and goes out as a menu does, over `COME` and `GO`. It goes when another window or app takes the keyboard (written first), unless it is pinned; the click on the item that took the keyboard is not taken as a second click that opens it again (`JUST_SHUT`). ⌘W closes it. The note's editor outlives the window, so the caret, the scroll and the history are where they were when it opens again. The arrow is a popover's, as MiniNotes' `NSPopover` drew it (`arrow_path`): a round tip and sides that bend out into the card's top, its ground filled over the card's edge where they meet and its sides drawn in the edge's color, running on into the card's own; a triangle with straight sides read as sharp. The card's edge is a hairline of the ink (`edge`, 7% in the light, 13% in the dark), and its shadow is its own, a popover's (MiniNotes' `NSPopover` cast a light one): a soft wide layer a little under the card and a close one that holds its edge, light in the light appearance and deeper in the dark. The system's shadow is off (`sys::float_note_window`): for a window with the keyboard it is the deep one an app's main window casts, and with the hairline it read as a thick border. The window is `SHADE` wider than the card at each side and taller under it, transparent, for the shadow to fall in, so the card and the arrow stand `SHADE` in from the window's left. Whatever lays a ground at the card's corners rounds itself by the card's radius less its edge, since a clip in gpui is a rectangle and anything square there stands past the card's curve: the tree's foot, and the bottom fades of the tree and the note (`edge_fade_at`), each rounded on the corner that is the card's, the note's left one only while no tree stands beside it. A square fade read as a sharp corner whenever the note or the tree had more to scroll. It comes and goes by fading as a whole, as the system composes it (`Fade`, `sys::set_window_alpha`, 150 ms in and 110 ms out, eased): drawn once at full ink and kept unseen until its first frame, its shadow fading with it. Tried and dropped: fading its words' opacity with a small drop, which cast the shadow anew from a half-drawn card at every frame and blinked; the system's own motion for a window coming is turned off, as it ran over the fade.
- **Its arrangement is the main window's.** A row across the top: the sidebar's button (`icons/panel-left.svg`; ⌘⇧B too), the tabs, Open in Onyx, and the pin at the right edge (Pin the Window, ⌘⇧P while the note's window has the keyboard and nowhere else, bound in its own key context `menubar::CONTEXT`; pinned, in the accent on a tint of it, and the sidebar's button the same while the tree shows). Open in Onyx is an icon as the pin is, at its left (⌘⇧O, in the same key context, over the main window's Choose Container… while the note has the keyboard). Tried and dropped: Open in Onyx in the tree's own row, by the vault's name, which hid it with the tree. The tabs have no plus here (`Tabs::from_start`): a note is made from the tree's plus or the landing page's New Note, and the row ends the head's gap from the buttons after it. Under it the vault's tree at the left, on a ground a shade toward the main window's frame (the frame's color over the note's at 0.08: darker in the light, nowhere near the frame), and the note at the right, its name over its words as the main window has it (below), drawn as it reads: MiniNotes' three ways of showing a note (source, edit, read) are gone, the marks shown where the caret is as in the main window. The tree slides shut and open over `SLIDE` as the main window's sidebar does, from wherever a slide still running had got (`toggle_tree`, `tree_t`), drawn at its full width in a box that grows, and whether it shows is kept (`menu_tree`). Its width is the person's, as the main window's sidebar's (`menu_tree_w`, `TREE_W` to begin with): a strip `GRIP` wide over its edge (`render_tree_grip`) lights a line under the pointer and takes a drag, between `TREE_MIN` and `TREE_MAX`, two fifths of the card, so the note keeps the most of it; left of `TREE_FOLD_AT` the tree folds away, and brought back out in the same drag it opens again. A double click goes to the width at which the rows in view and the vault's name are not cut (`tree_fit`), up to the same most, over `SLIDE`. A name the width cuts short says itself whole in a tip under the pointer (`tree_row`, its words measured against the room its row leaves them). The line the strip lights runs the tree's whole height. The held edge is heard in the capture phase, as the main window's.
- **The note's name** stands over its words with the soft line under it, as in a tab of the main window (The note's name, above): a `Textarea` of the tab's own (`title_field`), made the first time the tab is drawn since a field needs the window. ↩, the keyboard leaving, or the tab closing keeps it (`keep_title`, `keep_name`); Esc puts the file's name back. The note is written first, then renamed through `vault::rename`, and everything that knows it by its path follows (`MenuNote::follow_moves`): the tab's editor and its watcher, the closed tabs, the tree. The main window follows at its next frame (`Shell::moved_elsewhere`), and a rename or move made there reaches the note's tabs the same way (`menubar::moved`, from `follow_moves`, a moment on). MiniNotes' author line is gone; About has it. The sidebar's button stands at the row's left in every state, the tree shut or open with a tab or without, and the tabs start right after it (`Tabs::from_start`: the main window centers its pills; in the note's small row that left room after the button for nothing). With no tab open the row holds the button, Open in Onyx, which then shows the main window itself, and the pin.
- **Tabs.** A note picked in the tree, made there, or found by a wikilink in a tab (`open_note_link`; one it does not find is the main window's) opens in a tab at the end of its folder's pill, or shows its tab when it has one (`open_tab`). The row is the main window's (`tabs.rs`, The tabs): a pill for each folder with its mark, tabs and pills dragged into another order, and ⌘ held for the numbers; no plus (above). Its width is figured from the card's, less the sidebar's button, Open in Onyx and the pin, as the main window figures its own. Each tab is its own `Editor`, written and watched on its own, as a tab of the main window is, so the rules below hold for each: the main window's tab of the same note writes it, and the global's list of paths is what `holds` reads. A folder's right click in the tree offers New Note and Icon and Color…, the main window's sheet over the card. ⌘W closes the tab showing (with none, the window), the one after it showing, else the one before; ⌘⇧T opens the last closed again; ⌘1 to ⌘9 show a tab, ⌘9 the last; ⌘N names a new note in the tree, in the folder of the note showing. The tabs and the one showing are kept (`menu_tabs`, `menu_note`). With the last closed, the landing page shows: the vault's page of the main window made small, its drawing (`Shell::home_figure`, with a spring of its own) and the greeting, then New Note and, when a closed note is still there, Reopen Closed Tab, each a pill with its keys, as wide as the widest.
- **The tree** is where a note is chosen or made, and nothing of it is a panel of the system's: a note is picked from it, not from the file manager's open panel, and named in place, not in its save panel (MiniNotes' were the system's, and the first build here kept them). Its row: the vault's name, whose menu lists the vaults Onyx knows (the main window's, then the recent ones, each still there) and Open Onyx, where one is opened or made, and a + for a new note at the vault's top. Under it the vault's folders and notes as the sidebar has them (`vault::tree`, read off the window's thread each time the window opens): a chevron, Catppuccin's icon and the name, the note held lit, a folder opened and shut over `FOLD_ANIM`. A folder shows a + under the pointer, New Note in it. A new note is a row where it will stand, its field holding the first free "Untitled" selected to type over; ↩ makes it (`vault::create`) and holds it, a name refused (taken, empty, a slash) is said at the tree's foot in the window's language and the row stays, and Esc, another row, a press in the note or another vault leave nothing behind. The vault shown first is the one holding the note held, else the one shown last (`menu_vault`), else the main window's. With no vault known, the tree offers Open Onyx, and nothing else. A note outside every vault Onyx knows is still held and written; the tree shows a vault, not its folder.
- **The note** is the window's own `Editor`, set from the settings as a tab's (`Shell::look_of`, the writing check), in the main window's gutter, with a press under the words putting the caret at their end. It is written as a tab's note is: two seconds after its first change, and as the window goes, at quit, or before another note is held. Its folder is watched alone (`vault::watch_folder`, not recursive: a note may be in the home folder), and a change on the disk is taken as a tab's (`take_disk`). Its right click is the main window's note menu (`note_menu.rs`); a choice the main window carries out (a link to a note, a file opened or renamed, Export…, Print…) opens the note there first.
- **Open in Onyx** (⌘⇧O) writes the note, closes the window, and shows the main window (opened when shut) with the note in a tab, in the vault that holds it: the open one, else one Onyx has opened before, the deepest, else the note's own folder (`menubar::vault_of`, `Shell::show_from_menu`). With no note held it closes the window and shows the main window.
- **The shortcut** is ⌃⌥⌘O to begin with, held as a system hot key from any app (`sys/hotkeys.rs`, `onyx_core::shortcut`, both Mado's), changed in Settings, Menu Bar, where it is recorded as Mado records one: a click and the keys, Esc to give up, Delete for none, a key with no ⌘, ⌥ or ⌃ said why not (`sys/keys.rs` takes the keys before gpui while recording, and the hot key is let go meanwhile, so pressing it records it). Settings, Menu Bar also hides the item and turns Open at login on and off, which the system keeps (`SMAppService`). Its status takes about a fifth of a second to come back in a bundle, so it is asked off the main thread as the app starts, as the settings open and as Menu Bar is chosen, and the switch shows the last answer meanwhile (`Shell::read_at_login`); asked on the press, it held the window; a launch at login starts with no window (`sys::launched_at_login`, the open event's `keyAEPropData` is `lgit`).
- **Each window points the scroll router at its own scrollers** as it begins to draw (`cx.set_global(Router(…))`), since a frame in a note names itself to whichever window draws it.
- **Unchecked:** an input method composing in the window (keys posted to the copy's process reach the note and the name's field, `docs/probing.md`), and the shortcut pressed from another app; the probe opens the window as the item does.

## Menus

A right click opens a menu of the app's own (`menu.rs`, `Menus`), one card for every menu here and in the settings window, after emaki's: a card at the pointer kept inside the window, over a clear sheet that a click, a right click or Esc puts away, in over `MENU_IN` and out over `MENU_OUT`. It stands over everything, the search palette and the sheets too. A row is 30 tall with a 15 icon, a little tighter at the left because an icon's drawing stops short of its box, and the card is as wide as its longest row. The order and the icons are in `docs/design.md`, Menus.

Cut and Copy show only with a selection and Paste only with something on the clipboard, and the line under them goes when none do. The window makes every menu, the note's too: the editor says where and what it was on (`EditorEvent::Menu`). A text's choice is sent to the text it was opened on (`menu::do_edit`, `menu_focus`), which takes the keyboard only then: a right click on a link or in the margin moves nothing, or the marks on the caret's line would wake. A field calls its handler from inside its own update, where it cannot be read, so its menu is made a moment later (`window.defer` in `input_menu`); reading it there aborts the app. A press in an edge fade opens nothing, as it does nothing else there. Not offered, though emaki's files offer them: Cut, Copy, Paste and Duplicate of a file, which need a clipboard of files.

## The sheets

`render_sheet` draws one: a card over a scrim with a title, what it asks, its pills and a line of keys; Esc or a press off the card lets it go, and the card occludes, so a press in it let go outside does not close it. Each sheet's name is in the toolkit's `Input` (`rename_input`, `vault_input`, each made with the window, since an input watches the window it was made in), and ↩ keeps it through the input's `PressEnter`. The rename sheet (`render_rename`) and the new-vault sheet (`render_new_vault`) are the two of this kind, and the export sheet (`render_export`, `docs/export.md`) is drawn on the same scrim, wider, with the page in it; one is up at a time. After a sheet the keyboard goes back to the editor when a note is open, else to the window.

## The settings

`settings.rs`, the studio's window: a rail of sections, the page at the right, drawn from the main view's state so a change shows in both windows. General is Emaki's Appearance and more (`general_rows`): You (the picture, Choose… and Remove, and the name in a field the controls' width), Container (one row, the card's edge split in two by a hairline: the path as a person reads it, set as a path reads, in the code face with iCloud's cloud or a folder before it and the separators lighter, a press showing it in the Finder; and Change…; each half lights whole under the pointer, so no button's edge stands inside the card's), Window (the theme and the accent's discs, the chosen one named under Accent), and Text: Size, the words' and code's each on a stepper on one row (`EditorConfig::size`, `TextSizes`), with a button back to Medium's 16 and 14 pt once either left it; then the spelling and grammar check, its language on the same row beside its switch. A settings file from the presets (Small, Medium, Large, Custom) is read into the two sizes at load (`EditorConfig::one_size`). Each row earns its place: General fits the window unscrolled, so a new row means two old ones become one. The window's language is at the right of General's title. Font is the three faces' tiles (`fonts_rows`, Design, A note's words), at the measures of emaki's Fonts page so the page fits the window. A menu a settings row opens (the window's language, the spelling's, a field's Edit menu) is the settings window's to draw alone (`settings::menu_is_ours`): both windows draw the main view's menus, each at the place in its own coordinates, so one the main window drew too stood in two places. Menu Bar shows or hides the item, records the menu bar note's shortcut and turns Open at login on and off (The menu bar note, above). About has the title card, Alkaline Software presents with the studio linked, and the updates. A change to a face or a size reaches every editor through `Shell::push_look`.

## What the window remembers

`ui_state.rs`, `~/.onyx/state/ui.json`: the bounds (from `window_bounds()`, never `bounds()`), whether the sidebar is open and how wide, the settings' section, the vault, the note, the mode, the notes shown wide, the recent vaults, the open folders of the vault shown, the folder the last PDF went to, the menu bar note's tabs and the one showing, the vault its tree showed last and whether the tree shows (`menu_tabs`, `menu_note`, `menu_vault`, `menu_tree`). Written when any of it changes (the bounds at most every two seconds), at quit, and when the close button closes the window. The writing is a thread's own (`UiState::save_later`, `Shell::save_ui`), the saves in the order asked: `write_atomic` flushes the file to the disk, some 5 ms on an SSD, and a frame is not to wait on that for a tab moved mid-drag or a folder opened. What was last asked is kept and is what `UiState::load` gives, so a state read, changed and written again never misses one still on its way. The window's close (`Shell::save_ui_now`) and the app's quit (`UiState::flush`) wait for the disk, since on Windows and Linux the close ends the app.

## Probing

`ONYX_VAULT=<folder>` opens that vault instead of the remembered one, `ONYX_NOTE=<file>` that note; `ONYX_GO` steps: `note` (the first note), `notes` (the first three, as tabs), `close` (⌘W), `sidebar`, `menu` (the first note's menu), `rename` (its rename sheet), `vault` (the new-vault sheet), `live`, `source`, `reading`, `end`. With `HOME` pointed at a scratch folder the sheet finds no iCloud Drive and makes the vault in that folder's `Documents`, so a probe can press ↩ without touching the person's iCloud. `ONYX_SETTINGS=text` opens the settings on that section (`docs/probing.md`).
