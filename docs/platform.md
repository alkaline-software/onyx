# Platforms

How Onyx works on macOS, Windows and Linux, each on Intel-class and ARM machines, and on an iPhone and an iPad, and what is gated. The studio's standards have the reasoning; this is what Onyx itself does.

## Rules

- **Everything Unix-only is gated with a stated fallback.** Onyx's own code has no `cfg(unix)` of its own: the vault is `std::fs`, the trash is the `trash` crate (the Finder's, the Recycle Bin, the XDG trash), the watcher the `notify` crate (FSEvents, ReadDirectoryChangesW, inotify). The per-system calls are the template's, in `sys.rs`: open a file or a link, reveal a path (Finder, Explorer, else the folder opened), the window's ground, the languages, a picture of the window for a probe (macOS only; elsewhere it says so), and the traffic lights' fold (`sys::fold_lights`: on a Mac the main window's buttons are moved between gpui's row and a column at the rail's head as the sidebar folds, through AppKit's standard window buttons, and watched so gpui's own placing at a resize or a change of key window is undone at once; nothing in full screen, nor until the buttons have stood in a row once, which is where their pitch is read; elsewhere nothing, and the window's own buttons stay where the system draws them).
- **The system's spelling and printing are the Mac's alone** (`sys::spelling`, `spelling_fixes`, `print_pdf`). English is checked in the process on every system; elsewhere the other languages mark nothing, and a note to print opens in the system's PDF viewer.
- **A note on paper is the same on every system.** Typst is all Rust and the carried faces go with it. Only what a note's own fonts lack differs: `fonts::system_fallbacks` names each system's, and `fontdb` finds them by name, and the machine's fonts named in the settings too (Monaco on a Mac).
- **Every child process starts through `onyx_core::process::command`**, so none opens a console window on Windows. Onyx starts none of its own today; the update does.
- **The window's place is saved from `window_bounds()`**, never `bounds()` (`ui_state.rs`).
- **A key is named as the Mac has it and bound as `secondary-<key>`**; off a Mac the caps say Ctrl and Alt.
- **The menu bar is the Mac's alone** (`sys/status_item.rs`, `sys/hotkeys.rs`, `sys/keys.rs`, `sys::launches_at_login`): elsewhere `install_menu_bar` and `install_hot_keys` give nothing, the note in the menu bar never opens, and Settings, Menu Bar has nothing to change. A tray on Windows and Linux is left for when they are published.
- **What an iPhone and an iPad cannot do is gated with what happens instead**, as for the others (iPhone and iPad, below): no shell (`terminal_none.rs` stands in the terminal's place), no menu bar note, no second window (the settings are a sheet of the main one), no panel to choose a folder or a file in (the container is fixed, `sys::fixed_container`), no file manager to show a file in and no printing (their choices are left out of every menu, `menu::NOT_HERE`), and no update of its own (`update::from_store`).
- **A key binding is made through `sys::key`**, never `KeyBinding::new` with `secondary-` in it: gpui reads `secondary-` only where it is told the system (`KeyBinding::load`), and there gives an iPad's keyboard Ctrl. `sys::key` makes it ⌘ on a Mac, an iPhone and an iPad, and Ctrl elsewhere.
- **A note's line ends are plain.** A file with Windows' is read as plain ones and written back plain (`lines::Doc::from_text`).

## macOS

The bundle is cargo-packager's with `macos/Info.plist` merged in: the languages, and Markdown as a document type Onyx edits, so Finder offers Onyx for a `.md` file. It has no `LSUIElement`: Onyx is a Dock app with an item in the menu bar, not a menu bar app, so it stays in the Dock and ⌘-Tab with its window shut. Its item, its hot key (Carbon's `RegisterEventHotKey`, which needs no permission) and Open at login (`SMAppService`) are Mado's; the item's place is kept by the system under the autosave name `OnyxNote`. The dev build is a bundle of its own in `target/debug/dev.noindex/` (`scripts/dev-app.sh`). The installer is a notarized disk image (`docs/release.md`).

### iCloud Drive

Onyx's own iCloud container, when the bundle has one, is the container to choose for vaults kept in iCloud: the folder Finder shows in iCloud Drive as an "App Library" named Onyx with the app's icon on it, as Obsidian's (`iCloud~md~obsidian`) is. The container is asked of the system at launch on a thread of its own (`sys::warm_icloud`, `NSFileManager.URLForUbiquityContainerIdentifier`, which can take a moment the first time and is never asked on the main thread), and its `Documents` folder, the part iCloud Drive shows, is made then, so the system's folder panel behind Choose Container… shows it in iCloud Drive as Onyx. The container exists only for a bundle signed with the iCloud entitlements (`macos/Onyx.entitlements`: the container `iCloud.com.alkalinesoftware.onyx`, CloudDocuments) and a Developer ID provisioning profile that names the container, embedded as `Contents/embedded.provisionprofile`; `Info.plist` names the container under `NSUbiquitousContainers`, public in document scope, so iCloud Drive lists it. `release-mac.sh` does both when `ONYX_PROVISION_PROFILE` is set (`docs/release.md`, One-time setup). A bundle without the profile, the dev build among them, cannot carry the entitlements (the system kills such a bundle at launch), so there the container is `None`, and a folder of the person's own in iCloud Drive, chosen in the panel, is synced by the system like any other.

## iPhone and iPad

The same app, drawn by gpui's own backend for them (`gpui_ios`: UIKit, Metal, CoreText, carried in `vendor/gpui_ios` with five changes, `UPSTREAM.md` there), built for `aarch64-apple-ios` and, for a simulator, `aarch64-apple-ios-sim`. It is checked in simulators (an iPhone 17 Pro Max and an iPad Pro on iOS 26, an iPhone SE on iOS 18) and on an iPhone 17 Pro (On a device, below); what has not been tried is under Not checked.

- **The bundle** is made by `scripts/ios-app.sh`, since no packager makes one from a Cargo manifest: the executable, `ios/Info.plist` (the whole of it: gpui's scene delegate `GPUIIosSceneDelegate`, the launch screen as a color, the orientations, the screen's own pace on an iPhone (`CADisableMinimumFrameDurationOnPhone`), the languages, Files' access to the app's Documents, the iCloud container), and `ios/Assets.xcassets` compiled by `actool` (the icon, the full square with no alpha channel, from `make-icon.sh`; `LaunchGround`, the frame's ground light and dark). `IPHONEOS_DEPLOYMENT_TARGET` in `.cargo/config.toml` is the oldest system, iOS 17, for the compiler and every C dependency, and the script writes it as `MinimumOSVersion`.
- **The container is fixed** (`sys::fixed_container`): Onyx's iCloud container when the bundle has one, the Mac's own (`iCloud.com.alkalinesoftware.onyx`, `ios/Onyx.entitlements`), so a vault made on either is on both; else the app's own Documents, which Files shows as On My iPhone, Onyx. An app there reaches no other folder and gpui has no folder panel, so Choose Container… and Close Container are not offered, and Settings, General says where the container is. The iCloud answer is waited for at launch, up to a second and a half (`sys::await_icloud`), since the first page drawn is the container's vaults.
- **The app's own folder moves** when the app is updated or restored (`…/Containers/Data/Application/<a new id>/`). Every path the window remembers is read through `sys::rehome` (`UiState::rehome`), which takes a path under an older folder to the same place under this one. The settings and the state are in `Library/Application Support/Onyx` there (`paths::root`), not `~/.onyx`: the one place an app may make a folder that is backed up and that Files does not show.
- **The vault's watcher is Onyx's own** (`onyx_core::watch`): the `notify` crate's watcher there opens a descriptor for every file of the tree, and an app may hold a few hundred. Onyx's holds one for each folder, lists a folder again when it changes and says what came, went or has another time or length. A note another app writes in place changes no folder, so every folder is listed again when the app comes back to the front (`vault::look_again`, from the window's activation), the only time that can have happened.
- **The trash** is `NSFileManager.trashItem` (`vault::trash`), Recently Deleted in Files. The system has one only for what is in the app's Documents or in iCloud; what Onyx holds out of a vault (`file_undo`) is under its support folder, so such a thing is moved into Documents first and trashed from there. In a simulator both end in `Documents/.Trash`.
- **The keyboard comes out for a handler that says it takes text and how long its text is.** gpui's backend asks `accepts_text_input` and `text_length_utf16` before it takes the keyboard's focus: the editor answers the first with yes there alone (on a Mac it says no, for its keys' sake, `docs/editor.md`), and with no while it reads only, so a note that takes no change brings no keyboard out, and the toolkit's fields are given the second (`vendor/gpui-component`, `UPSTREAM.md`). A handler missing either shows a caret and no keyboard. The system may put the keyboard away with the words still its owner (a finger drawn down into it), so a press in the words asks for it again (`Window::request_virtual_keyboard`).
- **What the system keeps of the window is left clear** (`Shell::safe`, from `window.insets()`): the status bar, the home indicator, the sides of a turned iPhone, and the keyboard while it is out. The window's parts are laid out in the room that is left, on the frame's ground, and the status bar's ink is light on the frame, which is dark in both appearances, and follows the page in a compact window, whose note runs under it on its own paper (`sys::status_bar`; `docs/window.md`, A compact window).
- **A finger is read by gpui**: a tap is a press and a release, a pan scrolls with its own momentum through the scroll router, a swipe from the screen's edge is `on_back_gesture`. A finger held still is the right button (`Shell::render`'s listener for `LongPressEvent`), so every menu a right click opens is there, but in a note's words, which are the system's text's (below). Nothing follows a finger as a held button follows a pointer: an edge is not dragged, and a row or a tab is not moved.
- **Words are selected as the system's own text views select them** (`editor/touch.rs`, `sys/text_touch.rs`). A double tap takes a word and a triple a line. A finger held on words picks up the caret with the system's loupe over it (`UITextLoupeSession`) and lets it go where it lifts; in a note that reads only it takes the word and runs by words. The selection's two ends have handles as the system draws them (a bar as tall as the caret, a knob over the start and under the end, in the caret's ink), which a finger that lands on one drags, the loupe over the end it moves (a `TouchDragEvent` claimed as it begins, so the page does not scroll); an end does not pass the other. A double or a triple tap, a hold or a handle let go, and a tap on the caret where it stands bring the system's edit menu over the selection (`UIEditMenuInteraction`, its words the window's own: Cut, Copy, Paste, Select, Select All, as the words allow), whose choices come back to the window as actions on the words that have the keyboard (`sys::listen_edit_menu`); it follows what it stands over as the page scrolls and goes when the selection changes. A finger held on a link, a picture, a task's box or a table's handle is not the words' and keeps the app's menu. The caret is not taken where a finger lands, as a handle is: the second tap of a double one lands where the first put it.
- **A touch keyboard corrects, capitalizes sentences and suggests**, as in the system's notes (`Editor::text_input_configuration`, and the toolkit's fields, `vendor/gpui-component`, `UPSTREAM.md`, 79), but in code and HTML and in a field kept `plain` (a link's address); gpui's default turns every aid off, and a note's name came out in small letters with no suggestions. Its Return in a field where Enter submits (a new note's name, a rename) submits, as the key does (78); it arrives as a line break typed, never as the key.
- **gpui acts on a touch only once it knows what it is**, a tap at the lift and a scroll at the first move, and it draws no hover's style after a touch, so nothing under a finger said it was felt until the finger had left. What a finger presses lays `widgets::press_light` first in itself: a wash of the ink while a finger rests there, asked for 90 ms after the finger lands (`Shell::finger_down`), as the system's own lists wait, so a finger that lands to scroll flashes nothing. The window hears the landing as gpui's offer of a touch drag (`TouchDragEvent`, which nothing claims). When the press is over, by a lift, a scroll begun or a held finger's menu, the pointer gpui left where the finger touched is sent off the window (`Shell::finger_done`): left there, an `on_hover` listener under it stayed on. A new thing a finger presses needs the light, or it is the one thing on the screen that does not answer.
- **A fling goes on by gpui's own count for as long as its speed lasts**, a second and more after a hard flick, whether its scroller reached its end at once or not, and a touch while it counts is read as one that stops the fling, never a tap: a list flicked to its end took no press for that long. The router says when an event moved nothing (`Scrollers::spent`), and the window ends the fling there with a touch of its own making, begun and taken back at once (`Shell::end_fling`), the one thing that ends gpui's count.
- **A press gpui reads as a pan is a press all the same** (`Shell::finger_pan`). gpui decides what a touch is before it knows what is under it: one that moved ten points is a pan (eight until the backend gave its own tuning, `vendor/gpui_ios/UPSTREAM.md`), and one that lands while a fling still counts stops the fling wherever it lands, and neither is ever a tap. A button of the system's takes both, nothing there being scrolled, and a thumb stretched to a corner rolls: the sidebar's button took one press in a few, and after a flick of the note no button answered for two seconds and more. The window follows each finger's pan and, when the finger lifts, presses where it began in two cases: the pan began on a thing a finger presses (`widgets::pressed_at`, the places `press_light` was laid in the frame) over nothing that scrolls, and went no further than `ROLL`, 24 points; or the touch landed during a fling outside the scroller that was flinging and stayed within a tap's reach (the note still coasts and a button on the bar is pressed). A pan begun over nothing that scrolls leaves no fling to count. What floats over a scroller and is no part of it says where it is (`Scrollers::fixed`: the bar at the foot, the sidebar's button), so a gesture begun on it belongs to nothing that scrolls and the note under it stays still. The sidebar's button stands at the screen's edge, where a press that rolls is the system's edge swipe by then: such a swipe begun on the button and let go within `ROLL` is the press it was (`side_pull_goes`), and a second tap in a row there is not a second press.
- **Nothing under a finger comes and goes with a pointer.** What a pointer's hover brings on a Mac is brought another way there, or a tap flickers it on and off: a file's bar shows while its piece is the one selected (`Editor::pointer_on`, `Embed::settle_bar`), a tab's file keeps its bar, and the bar stays in sight while the piece is, below the page's fading edge, a frame being taller than what a phone shows of it (`frames_in_view`, `Embed::set_head_down`). A frame as wide as the page stood in the way of every pull up the note, so it scrolls by itself only while it is the piece selected, by a tap in it, and else the pull is the note's (`Embed::router`). A card is a link under a finger and a tap follows it; a picture's tap opens the viewer; a finger held on either selects it and gives its menu. The bar's buttons are a finger's size there (`HEAD_H` 44, `BUTTON` 34).
- **The keyboard comes only where it was asked for.** A text that takes typing and has the keyboard's focus brings the keys out, so focus is not given to a note's words for anything but a press in them: a piece selected leaves the keyboard where it is (`select_object`), a tap that opens the viewer gives none, what closes over the page gives the keyboard back to the words only when they had it before it came (`Shell::note_keys`, `focus_editor_or_shell`), and a compact window's drawer takes it from the note it comes over.
- **A file opens in the system's own viewer** (`sys::open`, Quick Look's `QLPreviewController` over the whole window, with its own button to close it and its way to share the file with another app; the system places that button, at the top left from iOS 27 and the top right on iOS 26, and it is left where the system puts it): a card of a file, a link to one, Open with Default App, and View on a file's bar, which every file has there. A page of the web opens in its app, as before.
- **What floats stands on the system's glass** (`glass.rs`, `sys::glass`). gpui draws the window into one layer and cannot blur what is behind an element, so a plate of glass is a view of UIKit's laid over gpui's: Liquid Glass (`UIGlassEffect`) on iOS 26 and later, the thin material before it. What is under such a view is blurred by it, so a plate's icons are drawn by the system too, in the plate, from the app's own files (an SVG drawn once to a template picture); a plate holds icons and washes, never words gpui would set in Onyx's faces, so a menu, a sheet and the sidebar stay gpui's own. The one place a plate holds words is a search's or a find's field and its count, which are the system's own (`glass::field`, a `UITextField`, and `glass::label`, a `UILabel`): its keyboard, input methods, clear button and Search key are the system's, and what it says comes back to the window as `glass::FieldEvent`s over a channel the window listens to. A plate with a field takes touches, the field's own and, on the rest of the plate, the next responder's, gpui's view. UIKit's text field keeps its input traits on an object of its own, so objc2's check of a message finds no such method on the field and they are sent bare (`trait_to`). A plate and its marks name themselves as they are painted (`glass::plate`, `icon`, `wash`, `field`, `label`) and the frame's are told to the system once it is drawn (`glass::flush`, which tells it only what changed); the views take no press, so the element that named the plate is still what is pressed. The views stack as gpui painted their plates, not as they were made (`bringSubviewToFront`, told only when the order changes): made in another order, the keyboard's bar stood over the find's bar laid at the same place. The glass moves as the system's does: Liquid Glass condenses into place as a plate comes (its effect set in a spring of UIKit's) and melts back as it goes while it shows (a field on it lets the keyboard go as the melt begins, not as it ends, so the keyboard leaves at a tap as Safari's does), and a plate a finger is on swells on a spring, more for a small button than a wide bar, the icon nearest the finger rising in it, and settles back as the finger lifts (a plate's hitbox read as `press_light` reads its own; placed by bounds and center so the scale holds). It answers from the finger's landing (`widgets::finger_down`), not after the wait `press_light` keeps, and a tap's lift waits for the swell to come whole (`SWELL`), so a short tap shows as a hold does, as the system's buttons answer a tap. Liquid Glass is the system's interactive glass (`isInteractive`) and takes the touch for its own light; UIKit sends a touch a view does not use on to the next responder, gpui's view behind it, so the press still reaches the element. The system's views stand over everything gpui draws: what gpui draws over a plate says so (`glass::cover` in a scrim, a sheet's ground, a menu's card; `cover_by` for a drawer or a viewer that says how far it has come), and a plate painted before a cover that lies on it fades as the cover comes and returns as it goes, while one painted after it (a sheet's own close button) stays. On glass: the bar at the page's foot, the bar over the keyboard and its button, the sidebar's button and the close button at the title row's other end, a phone's search and find bars, the settings' close button and the viewer's buttons. Elsewhere `glass::on` is false and each draws the plate it always did.
- **Search and find are Safari's on a phone** (`Shell::safari`, `render_safari_bar`): a bar at the foot, over the keyboard while it is out, of a round button that closes it, a pill with the system's own field (and, for find, its count) and, for find, a pill of the previous and the next. The foot bar's magnifier finds in the note showing, as Safari's finds in its page, and searches the notes on the vault's page; the drawer's searches the notes. The search's bar stands over what was showing, which stays in sight until words are typed; then the notes found cover it from the top on the page's ground. A press anywhere but a bar and a note found puts either away, as the X does (`find-off`, the search's own ground); the page still scrolls under the find, since the router goes by where a gesture begins. A field's words are put in it and the keyboard given or taken by a number asked once (`search_set`, `search_focus`), so a frame never fights a press the person made in it. While the keyboard is the note's, its bar stands where the find's would and the find's waits.
- **A pull past a scroller's end stretches and springs back** (`scroll.rs`, `stretch`): gpui holds a scroller's offset to its ends at every frame, so the router keeps how far a finger went past an end and the scroller itself is moved by UIKit's curve of it (`stretch_of`, a relative top where the scroller is laid out); let go it comes back as a spring, and a fling that reaches an end goes past it by its speed and comes back. The note, the sidebar, the assets, the search, the settings and the page before a vault stretch. A stretch held by a finger is not a spent gesture, or the window's end of a fling cancelled the finger's own pan.
- **What a note embeds stands the page's whole width on a phone** (`widgets::full_width`): a picture, a file's frame and a large card, whatever width the note asks, and its bar has no width or place to set and its edge takes no drag. A table stands the page's width too, its columns as wide as their words ask with the room left shared (`docs/editor.md`, Tables).
- **A note changed on another device comes while it is open** (`sys::follow_icloud`, a `NSMetadataQuery` of the container's documents, running while the app runs). iCloud tells the device a file changed elsewhere and brings it only when asked, or when a query is running, as this one is; it lands in place, which changes no folder, so the vault's watcher never heard it and the note stayed as it was until it was opened again. Each file seen older here than in iCloud is asked for if it is not already coming, and once it is the newest the window has the vault looked over (`sys::icloud_landed`, `vault::look_again`), which finds it as any write from outside and joins it into the open note. On an iPhone 17 Pro a line added on the Mac was in the open note about a minute later, iCloud's own time.
- **The person's name comes from the Mac** (`sys::share_name`): an iPhone tells an app no name, so a Mac's Onyx writes the name it greets by into `Profile/name.txt` in Onyx's iCloud container, outside its `Documents`, which iCloud Drive does not show, and an iPhone's reads it at launch on the container's thread (a few seconds at most) as the gray name in Settings and the greeting's.
- **A picture for the person is chosen in the system's picker of the photos** (`sys::pick_picture`, `PHPickerViewController`, which needs no leave to read the library): the picture is drawn as it is seen, its short side at most 1024 points, written as a PNG and kept as on a Mac.
- **A menu keeps clear of what the system keeps** (`widgets::float_margin`): gpui holds a menu inside the window, and the keyboard is part of the window there, so a menu opened low stood half under the keys.
- **Every step of the edge swipe is sent to where it began**, and what claimed it has moved from under there by the second (`docs/window.md`, A compact window): the steps after the first are heard by the window, not by an element.
- **No tooltip comes after a touch** (`vendor/gpui-component`, `UPSTREAM.md`, 77): gpui leaves the pointer where a tap ended, so the button tapped was hovered from then on and showed its tooltip, keys and all, until the next touch. The keys themselves are bound as on a Mac, for a keyboard joined to the device. gpui's backend reports no pointer's hover there, a trackpad's on an iPad neither, so no tooltip shows on either yet.
- **One file is open at a time on an iPhone** (`sys::one_file`), with no tabs' row; an iPad has the Mac's tabs (`docs/window.md`, A compact window).
- **A window narrower than 720 is compact** (`docs/window.md`, A compact window): an iPhone upright, an iPad's narrow window.
- **Left out for now:** Export and printing (the sheet is laid out for a wide window and ends in the save panel), the system's spelling for languages other than English (`UITextChecker` is not asked yet), and a picture pasted from the clipboard (gpui's clipboard there is text).

### On a device

A release build is put on an iPhone 17 Pro (`scripts/ios-app.sh --device`, signed with the Apple Development certificate, `ios/Onyx.entitlements` and the development profile, under Onyx's own identifier): it installs, starts, and works in the hand as in the simulator, with the vaults of Onyx's iCloud container. A device takes the build only when it is registered in the developer account and named in the profile, and with Developer Mode on, which the device offers in Settings once a build has been sent to it (`docs/release.md`, One-time setup).

What a device showed that a simulator could not, each measured there with `ONYX_TRACE` (`docs/optimize.md`, the log):

- **A file in iCloud may be on the device by its name alone**, its contents fetched when it is first read, and that read waits for the network: 1.0 to 1.6 seconds for a note of a few hundred bytes, on the window's thread, at every note not opened on that phone before; a PDF a note embeds the same, in the layout. A Mac keeps its files, so it was never seen there. `vault::at_hand` says whether a file's contents are here (one `lstat`, the system's `SF_DATALESS` flag), and nothing on the window's thread reads a file that is not: a vault is asked for whole as it is shown and as the app comes back to the front (`sys::bring_vault`, `NSFileManager.startDownloadingUbiquitousItem` for each file not at hand, on a thread of its own), a note pressed before it has come is read on a thread of its own and opens when it is here, its row wearing a cloud meanwhile (`Shell::await_note`), a picture or a PDF's size is not read until the file has come (`Pictures::size_of`, `waiting`), and a vault's folder looks likewise (`folder_look::ensure`). A simulator's files are the Mac's and are always at hand; `brctl evict <file>` on the Mac makes one that is not.
- **The screen draws 120 frames a second and gpui's display link asked for 60** (`vendor/gpui_ios/UPSTREAM.md`).
- **A frame waited for its drawable.** gpui's backend paced the window from a `CADisplayLink` and took each frame's drawable from the layer, which waits until the compositor lets one go: once one frame fell behind, every frame of that scroll slept out the rest of its 8.3 ms on the window's thread, and it began so at whole launches. A simulator never shows it. Each window has a `CAMetalDisplayLink` of its own now, which brings the drawable with the frame (`vendor/gpui_ios/UPSTREAM.md`, 5).
- A frame of a note scrolling is 1 to 3 ms there, with pictures, frames and cards in it or none, and a key typed changes the text in a tenth of one.

### Not checked

Not tried yet: the system's field of a search under a real finger and the system's keyboard, the glass's spring under a real press, the picker of the photos on a device, an iPad itself, glass on a system before iOS 26 (the thin material, seen in no simulator yet), Recently Deleted as Files shows it, a hardware keyboard and a trackpad on an iPad, the screen turned, Split View and Stage Manager, and a vault with no network while its files are not at hand (a note pressed then waits with its cloud until the network is back). A probe's touches go through gpui's reading of them, and typing through UIKit's `insertText:` (`docs/probing.md`), not through the screen, so what a real finger and the system's keyboard do is seen only on a device.

## Windows and Linux

As the template has them: Velopack's installer and the Store's `.msix` on Windows, a `.deb`, an AppImage and a snap on Linux, the window's own buttons where the system draws none (`csd.rs`). Neither has been tried on a machine yet for Onyx, and no release carries them; the release's step 6 tries them in VMs once one does.

## The assets' player

A video or a sound in an asset's tab plays in the system's web view through `wry` (`media.rs`): WKWebView on a Mac, WebView2 on Windows, a child of the window drawn over gpui. Linux has no web view that can be set in a gpui window, so there `Player::open` gives none and the tab says the file plays in its own app. `wry` is a dependency on the Mac and Windows only.
